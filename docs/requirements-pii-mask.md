# Requirements: PII/secret masking layer (encode/decode)

Status: draft for review · Owner: klerik3d · Target: gurt Electron MVP (this repo)

This document is a work order for an implementing agent. Read `README.md`
first. Key code: `src/main/sessions.ts` (`promptBlocks`, `onSessionUpdate`,
`session/prompt`), `src/shared/mcp.ts` (`MCP_DEFS`, `mcpDef` — the registry
pattern reused for detector backends, §4), `src/shared/credentials.ts`
(`CredentialKind`, `CREDENTIAL_KINDS`), `src/main/credentials.ts`,
`src/shared/types.ts` (`SessionInfo`, `AgentSessionRequest`),
`src/renderer/src/components/Sidebar.tsx` (the `git access` chip this
mirrors), `src/renderer/src/components/SettingsPage.tsx`,
`docs/requirements-git-access.md` (the closest existing precedent — a host
broker keeping one specific kind of secret out of the container). Do not
change the contract described here without asking the owner.

> **Scope**: this pass covers the user ↔ agent (ACP) seam and the settings
> that configure it only. Masking agent ↔ MCP tool traffic is explicitly out
> of scope — it is its own task, to be scoped separately once this seam
> ships. See §7.

## 1. Motivation

Today everything the agent sees carries whatever real data is in it: chat
text the user types, and everything the agent says back. Nothing stands
between the user and the agent's own context, the way
`requirements-git-access.md` already isolates *credentials* specifically
(the agent never sees a git secret; a host broker holds it and answers per
request). This generalizes that same idea from "git credentials" to "any
sensitive text the user types": the agent operates on typed placeholder
tokens, never real values, while the user's own chat view always sees the
real data.

## 2. The contract

- **encode**: scan text for entities a detector recognizes, replace each
  with a token (§3).
- **decode**: scan text for tokens, replace with the real value.
- Applied at one seam, never inside the agent's own context: the **ACP
  boundary** (`sessions.ts`) — user ↔ agent chat.

### 2.1 Direction table

| seam | direction | data | operation |
|---|---|---|---|
| user → agent | outbound `session/prompt` | user-typed prompt text | encode (real→token) before it reaches the agent's context |
| agent → user | inbound `session/update` (`agent_message_chunk`, `tool_call`/`tool_call_update`) | agent's own text / tool titles / detail | decode (token→real) before `push`/`append` into `s.entries` (what the renderer shows) |

The agent's own context therefore only ever contains tokens; the user's chat
view always operates on reals — "who is allowed to see real data sees it,
who isn't sees placeholders."

## 3. Token format

**Key policy**: gurt always generates the encryption key itself, on the
host, and never accepts one from an external component. Whether the
encryption runs in our own code or is handed to an external detector/
anonymizer backend (§4/§5.1) to execute, the key is ours — generated by
gurt, passed *to* the backend when a backend needs it to do the work, never
generated *by* it and reported back. Same posture as the credential policy
in `requirements-git-access.md` §2: gurt owns the secret material outright,
an external service is at most a processor, never the source of truth for
it.

- Self-contained and reversible without an external map:
  `<TYPE:ciphertext>`, where `ciphertext = AES-GCM(sessionKey, realValue)`
  (Node's built-in `crypto`; no dependency on Presidio's Python `AESCipher`).
- `TYPE` carries entity-type context to the agent (`EMAIL`, `PHONE_NUMBER`,
  `US_SSN`, `AWS_ACCESS_KEY`, …) without leaking the value — unlike a bare
  Encrypt-operator ciphertext, which is opaque even in type.
- `sessionKey` is per-session, generated at session start, held only in
  memory (alongside the rest of `sessions.ts`'s in-memory session state).
  Decoding is a pure function of the key, so no separate vault map is
  needed — a plain per-session lookup keyed by session id.
- Consequence: an in-memory-only key means tokens outlive their usefulness
  once the session's process ends — old chat history containing tokens
  becomes permanently undecodable after a restart, unless the key itself is
  persisted (§7 flags this as an open decision, not resolved here).

## 4. Detection

Pluggable, behind one interface (`Detector`):
`detect(text: string): Array<{ start: number; end: number; type: string }>`.

- **v1 built-in detector** — pure TS, regex/checksum only, **no new npm
  dependency, no vendored pattern files** — see §4.1 for where the patterns
  actually come from.
- **external detector** (optional, later): an HTTP call to a configured
  backend (Presidio analyzer, or any other), for the free-text NER gap the
  built-in detector explicitly does not cover. Backend selection is a
  registry, the same shape as `MCP_DEFS`/`mcpDef` in `shared/mcp.ts`.

### 4.1 Pattern sources (built-in detector)

No pattern data ships in the repo and no library is added to `package.json`
for this. Instead, the pattern *source* is itself a setting (§5.1): pick a
public, permissively-licensed collection (CommonRegex, Presidio's
`predefined_recognizers`, gitleaks' `gitleaks.toml`, or another one added to
the same list later) and gurt fetches it at runtime.

- **Fetch**: a plain HTTP GET of the raw source file, pinned to a specific
  commit/tag (never a moving branch) so patterns never change silently
  underfoot. Refetched only on explicit user action ("check for updates" /
  re-selecting the pinned ref), not on every launch.
- **Cache**: the fetched raw file plus its adapted form live under
  `~/.gurt/pii-patterns/<source>.json` — read from there on every start;
  the network is only touched on first selection or an explicit refresh.
- **Adapter**: one small per-source parser we write ourselves — pulls just
  the `{ type, regex }` pairs out of that source's own format (a Python
  literal list for CommonRegex/Presidio, the `[[rules]]` blocks of
  `gitleaks.toml`) into gurt's own pattern shape. This is text extraction of
  a handful of fields, not a full-fidelity parser — no TOML/Python-AST
  library needed for it either.
- **Offline / first run**: with nothing cached yet and no network, the
  built-in detector has no patterns to run and `piiMask` cannot turn on —
  surfaced as a plain configuration state in §5.1, not solved further here.

## 5. Settings: two-tier toggle

### 5.1 System settings (global)

New section in `SettingsPage.tsx` (pattern: Repos / Environments /
Credentials), picks the active detector backend:

- `built-in` — requires picking a **pattern source** (§4.1) from the same
  kind of list: CommonRegex / Presidio recognizers / gitleaks rules / …
  Selecting one triggers the fetch → adapt → cache flow; re-selecting the
  same source with a newer pinned ref re-fetches. Nothing is masked until a
  source has been fetched at least once.
- `presidio` — configure either "run locally" (gurt manages a docker sidecar
  the same way it builds/runs env images — `docker build`/`up`,
  content-tagged) or "remote" (URL + a `pii-detector` credential, §5.3).
- registry open to more backends later (mirrors §4's detector interface).

Nothing is masked while no backend is selected — this *is* "off".

### 5.2 Per-session toggle

- New `piiMask?: boolean` next to `gitAccess` on
  `AgentSessionRequest`/`SessionInfo` (`shared/types.ts`).
- New Session modal chip, same pattern as the `git access` chip in
  `Sidebar.tsx` (~line 736/1287) — **disabled** (not just unchecked) when
  §5.1 has no backend selected, with the reason shown inline.
- Default mirrors `gitAccess`'s "on when it resolves" precedent: on whenever
  a backend is configured, off otherwise.

### 5.3 Credential store

- New `CredentialKind`: `'pii-detector'` in `shared/credentials.ts`'s
  `CredentialKind` union + `CREDENTIAL_KINDS` (fields: `url`, `apiKey` — both
  kind-specific like every other entry). `hosts: []`, excluded from
  `isGitKind` (same treatment as `agent-token` today).
- No new storage subsystem — same `~/.gurt/credentials.json`, same CRUD in
  `credentials.ts`.

## 6. Where it hooks — `src/main/sessions.ts`

- Encode: wrap the `text` feeding `promptBlocks(...)` (~line 1411) before
  the `session/prompt` request — only when the session's `piiMask` resolves
  on.
- Decode: in `onSessionUpdate` (~line 1870), before `this.push`/`this.append`
  for `agent_message_chunk`/`agent_thought_chunk` (`u.content.text`) and for
  `tool_call`/`tool_call_update`'s `title`/`toolDetail(u.content)`.

## 7. Non-goals (this pass)

- **Agent ↔ MCP tool traffic — fully out of scope.** Tool call requests and
  responses (`src/main/mcp/manager.ts`, `githubServer.ts`) are untouched by
  this doc; real values still flow through MCP tool calls unmasked. Masking
  that seam is a separate task, scoped on its own once the ACP seam ships —
  do not fold it into this implementation.
- Free-text NER in the built-in detector (§4) — regex/checksum only; NER is
  deferred to an external backend.
- PII inside repository files the agent reads directly via its own
  in-container tools — only text crossing the ACP seam gurt controls is
  covered; raw file reads bypass gurt entirely (the same limitation the git
  broker has for anything outside git's own protocol).
- Deciding whether the session key persists across app restarts (§3) —
  flagged, not resolved: for v1, in-memory-only (tokens from a finished
  session become permanently opaque, treated as intentional auto-expiry, not
  a bug).
- `safeStorage`/encrypted-at-rest for the `pii-detector` credential kind —
  same tradeoff `requirements-git-access.md` §11 already accepts for the
  rest of the store.
